# Changelog

## [Unreleased]

### Added
- Workflows are grouped by feature on the pull request page: each feature (an actor and a goal) is a collapsible group with compact rows, one per technical path, and the step page shows the feature above the workflow title.
- Every workflow needs a `feature` and the number of workflows is no longer limited; a stored analysis is still capped at 5 MB.
- On desktop the step page panes are resizable and collapsible (workflow graph versus content; the step panel collapses to its title line) with draggable, keyboard-accessible handles, double-click to reset, and sizes remembered in the browser.
- Workflows are now business scenarios (an actor and a goal, with the outcomes as labelled branches) instead of entrypoint traces; each has an actor shown on the pull request page and the step page.
- Every changed file must be covered: a submission that leaves files out is rejected with the list of uncovered paths, and files without runtime behavior go in a separate "unassigned" list with a reason.
- The pull request page shows a coverage indicator ("28/60 files"), plus collapsible "Not in any workflow" and "Unassigned" lists.
- Steps can attach other changed files (wiring, schemas, migrations, tests); the step page shows them as file tabs above the diff, with `?file=` in the URL.
- Each workflow on the pull request page has a "Recompute" action with an optional instruction (up to 500 characters) that replaces just that workflow, keeping its address; it uses the model API button or a live-updating CLI command, and `#recompute-<id>` opens the panel.
- The pull request page always offers "Recompute all", highlighted when the pull request has newer commits.
- `POST /api/pr/[owner]/[repo]/[number]/workflows/[workflowId]`, the MCP tool `trace_replace_workflow` and the `trace_recompute_workflow` prompt replace a single workflow.
- The pull request list is cached in the browser; coming back shows it at once and syncs in the background, highlighting new pull requests and updating changed ones in place.
- Pull requests are split into workflows, one per entrypoint, each with an ordered list of steps.
- Workflows can be generated by a CLI agent through the MCP server (`trace_submit_workflows`, `trace_workflows` prompt) or by the configured model API.
- `POST /api/pr/[owner]/[repo]/[number]/workflows` generates workflows with the model API.
- Analyses and workflows are saved per pull request in a local SQLite database at `.trace/trace.db`.
- A Mermaid graph is produced for each workflow from validated data; agents never submit diagram text.
- The pull request page data includes a ready-to-paste Claude Code and Codex command and a stale flag when the PR has newer commits.

- The home page lists your open pull requests and links each one to its own page with a repository filter.
- The pull request page lists its workflows, warns when the analysis is for an older commit, and shows copyable Claude Code and Codex commands or a "Generate workflows" button when none exist.
- The workflow page keeps a clickable Mermaid graph pinned at the top with Prev/Next buttons and left/right arrow keys to move between steps.
- The app follows the system light or dark color scheme.

### Changed
- A workflow is now one technical path through a feature (one request, one outcome) and each step is exactly one file in execution order, so the diff shows a single file; steps allow up to 20 per workflow and submissions can no longer bundle files with `paths` (older analyses still show their file tabs). Recompute the pull request to get the new shape.
- The database moves to schema version 3 (a nullable `workflows.feature` column) on first start; existing analyses keep working and are grouped under their own workflow titles until recomputed.
- On the step page, ↓ and ↑ follow the graph (next step along the flow, back to where you came from) and ← and → switch to a sibling branch; the sibling nodes are outlined with dashes and the key hints dim when a direction has no target. Prev/Next keep the linear order; PageUp, PageDown and Space still scroll.
- Step summaries are one sentence (up to 200 characters) and each step lists 1-4 "what it should do" checks with green check icons; the step panel is much smaller so the diff gets the room.
- The analysis instructions (MCP prompts, model prompts, `docs/cli-agent.md`) now come from one guide that teaches business scenarios, full coverage and includes a worked example; older analyses still load unchanged.
- Recomputing one workflow keeps the files it covered covered, and up to 12 workflows are allowed.
- The workflow step page is full screen: a top-to-bottom graph fills a left third that scrolls on its own, and the step details and diff fill the right two thirds; on small screens the graph collapses above the content.
- The interface has an IDE-like look: tinted panes per region, monospace labels, entrypoint-kind colors, a signal-flow workflow graph with a step progress rail, a styled diff, and a status bar.
- The review diff flows with the page and scrolls sideways only, and the Mermaid graph runs left to right.
- Saved analyses now live in `.trace/trace.db` instead of JSON files in `.trace/reviews/`; earlier reviews are not migrated.
- MCP tools use `analysisId` instead of `reviewId`, and `trace_submit_walkthrough` is replaced by `trace_submit_workflows`.
- The workflow graph now uses the app colors and marks the current step with an accent border, tinted fill and accent label.

### Fixed
- The workflow graph on the step page now fits the pane width (with a 1:1 toggle and Ctrl/Cmd+wheel zoom) instead of being cropped on both sides, and Mermaid is preloaded from the pull request page.

### Removed
- The review sidebar, the reviewed checkboxes, the clickable symbol source dialog and the padded "additional changed file" steps.
- The heuristic walkthrough and the `/api/review` and `/api/reviews` endpoints.
